# 楽天モバイル キャンペーンナビ Codex引き継ぎマニュアル

この文書は、`mobile-campaign-navi` プロジェクトで今後作業するCodexが、これまでの要件定義・画面要件・データ設計・判定ロジック設計を同じ前提で判断できるようにするための引き継ぎ資料です。

新しいCodexは、実装や改修に入る前にこの文書を必ず読み、ここに書かれている方針を優先してください。

## 1. プロダクト概要

サイト名は **楽天モバイル キャンペーンナビ**。

楽天モバイルの新規入会・乗り換え時に、ユーザーが利用できるキャンペーンを診断し、**併用可能なキャンペーンの合計獲得ポイントが多い順にTop5で表示するWebサイト**。

### ユーザーIssue

楽天モバイルは新規入会キャンペーンを常時多数開催している。キャンペーン内容が似ているものが多く、併用できるもの・できないものも混在しているため、新規入会者が自力で最適なキャンペーンを探すのは難しい。

### Goal

ユーザーが数個の条件を選ぶだけで、以下が分かる状態にする。

- 現在申し込み可能なキャンペーン
- 自分の条件で利用できるキャンペーン
- 併用できるキャンペーンの組み合わせ
- 合計獲得ポイントが多い組み合わせTop5
- 各キャンペーンの主な条件・期限・公式ページリンク

### 公開前提

このサイトはプロトタイプではなく、実際に公開する前提。

そのため、以下を必ず守る。

- 楽天モバイル公式サイトではないことを明示する
- 広告・PR表記を表示する
- キャンペーン情報は公式サイトを確認して反映する
- ポイント数・条件・期限は変更される可能性があることを表示する
- 最終的な適用可否は公式ページで確認するよう案内する

## 2. スコープ

### 作るもの

2ページ構成の診断サイト。

1. 条件入力ページ
2. 診断結果ページ

### 作らないもの

以下は現時点ではスコープ外。

- ログイン機能
- 管理画面
- 診断結果の保存
- 診断結果の共有
- 個別キャンペーン詳細ページ
- キャンペーン比較表
- 自動スクレイピング・自動更新
- ユーザーの個人情報入力

## 3. ページ構成

### 3.1 条件入力ページ

目的は、ユーザーに「公式の大量キャンペーンを比較しなくても、自分に合う高ポイントキャンペーンTop5が分かる」と伝え、5問の診断へ進んでもらうこと。

#### ヘッダー

- サイト名: `楽天モバイル キャンペーンナビ`
- 広告・PR表記
- 最終更新日

#### ファーストビュー

添付されていた参考画像の方向性に寄せる。

伝える内容:

- 楽天モバイルのキャンペーンは多数あり、比較が難しいこと
- このページなら、ユーザーに合うキャンペーンを獲得ポイントが高い順にTop5で紹介できること
- 併用できるキャンペーンの組み合わせも考慮すること
- 5つの質問に答えるだけで診断できること
- 公式サイトではない旨
- 広告・PR表記

診断フォームはファーストビュー内に全部出さず、1回スクロールするとフォームが見える構成にする。

#### 診断フォーム

フォームは5問構成。

SIM種別は判定条件に含めない。  
申し込み方法はWeb限定・店舗限定キャンペーンがあるため判定条件に含める。

Q1. 楽天モバイルへの申し込みは初めて？

- 初めて: `first_time`
- 2回目以降: `repeat`

Q2. 他社からの乗り換えですか？

- 電話番号そのままで他社から乗り換え: `mnp`
- 楽天モバイルで新しい電話番号を取得: `new`

Q3. 端末の購入も考えていますか？

- iPhoneを購入: `iphone`
- Androidを購入: `android`
- 考えていない: `sim_only`

Q4. 楽天カードはお持ちですか？

- 持っている: `has_card`
- 持っていない: `no_card`

Q5. 楽天モバイルの申し込みはどちらで行いますか？

- 店舗から: `shop`
- Webから: `online`

#### 送信

ボタン文言:

- `この条件で診断する`

クリック後、診断結果ページへ遷移する。

条件はURLパラメータで渡す。サーバー保存はしない。

例:

```text
result.html?conditions=first_time&application_status=mnp&purchase_plan=iphone&rakuten_card=has_card&application_method=online
```

### 3.2 診断結果ページ

目的は、ユーザーが「どの組み合わせが一番ポイントを多く獲得できるか」をすぐ理解できること。

#### ページタイトル

以下のみ表示する。

```text
あなたが利用・併用できるキャンペーン
獲得ポイントTop5
```

以下は不要。

- 「最大で32,000ポイント獲得できる可能性があります」のような別見出し
- 入力条件の要約

#### ランキングカード表示順

各カードは以下の情報を表示する。

1. 順位
2. キャンペーンバナー画像
   - 複数キャンペーンの組み合わせの場合、最もポイントが高いキャンペーンのバナーを使う
3. 合計獲得ポイント
4. 組み合わせるキャンペーン名と各ポイント
5. 主な適用条件
6. 申し込み期限
7. 公式ページへのリンク

#### 公式リンク

ページ上部と下部に広告・PR表記を入れるため、ランキングカード内のリンク付近にはPR表記を重複表示しない。

#### 再診断導線

ページ最下部に `もう一度診断する` ボタンを置く。  
条件入力ページへ戻す。

#### 該当なし

条件に合うキャンペーンがない場合:

- 対象キャンペーンが見つからなかった旨
- 条件変更を促す文言
- 楽天モバイル公式キャンペーン一覧へのリンク

## 4. 非機能要件

### 対応環境

- スマートフォン優先
- PC、スマートフォン、タブレット対応
- 主要ブラウザ対応
  - Chrome
  - Safari
  - Edge
  - Firefox

### 表示速度

- 初回表示はできるだけ軽くする
- 診断結果はユーザー操作後、待ち時間を感じない速度で表示
- 画像・外部ライブラリは必要最小限

目安:

- 初回表示: 3秒以内
- 診断結果表示: 1秒以内

### 情報の正確性

- キャンペーン情報は楽天モバイル公式サイトを確認して登録
- 最終確認日をデータに持たせる
- 開始日・終了日・対象条件・併用可否・ポイント数を明確に管理
- 終了済み・開始前キャンペーンは表示しない

### 保守性

- キャンペーンデータはコード本体から分離する
- JSONまたはJSデータファイルで管理する
- 判定ロジックと表示文言を分ける
- キャンペーン追加・修正・終了対応がしやすい構造にする

### アクセシビリティ

「キーボード操作でフォーム選択と診断ができること」は要件から外れている。  
ただし、通常のフォーム部品・ラベル・十分なコントラスト・読める文字サイズは維持する。

### セキュリティ

- 個人情報を入力させない
- ログイン機能を持たない
- 診断内容をサーバーに保存しない
- 外部リンクは `rel="sponsored noopener noreferrer"` などを使う

### 法務・コンプライアンス

- 楽天モバイル公式サイトではないことを明示
- 広告・PR表記を表示
- キャンペーン内容が変更・終了する可能性を表示
- 最終的な適用可否は公式サイトで確認する旨を表示

## 5. データ設計

キャンペーンデータは1件ごとに以下の情報を持つ。

```ts
type Campaign = {
  campaignCode: string;
  name: string;
  summary: string;
  point: number;
  bannerImage: string;
  officialUrl: string;

  startDate: string;
  endDate: string | null;
  deadlineLabel: string;
  lastCheckedAt: string;

  priority: number;

  eligibility: CampaignEligibility;
  exclusions: CampaignConditions;

  combination: {
    cannotCombineWith: string[];
    combinationGroup: string | null;
  };

  userActions: string[];
  officialLinkLabel: string;
};
```

条件型:

```ts
type CampaignEligibility = {
  conditions: string[];
  application_status: string[];
  purchase_plan: string[];
  rakuten_card: string[];
  application_method: string[];
};

type CampaignConditions = CampaignEligibility;
```

空配列は「条件なし」として扱う。
`userActions` は、ユーザーがキャンペーン適用のために取るべき行動のみを書く。公式確認を促す共通文言、期間限定ポイントなどの共通注意書きは入れない。

`canCombineWith` は使わない。  
`cannotCombineWith` には、併用できないキャンペーンの公式キャンペーンコードを入れる。今回の方針では、`cannotCombineWith` に含まれていない組み合わせは併用可として扱う。

## 6. 診断入力データ

P1からP2へ渡す診断条件。

```ts
type DiagnosisInput = {
  conditions: "first_time" | "repeat";
  application_status: "new" | "mnp";
  purchase_plan: "sim_only" | "iphone" | "android";
  rakuten_card: "has_card" | "no_card";
  application_method: "shop" | "online";
};
```

URLパラメータの対応:

- `conditions` -> `conditions`
- `application_status` -> `application_status`
- `purchase_plan` -> `purchase_plan`
- `rakuten_card` -> `rakuten_card`
- `application_method` -> `application_method`

## 7. 判定ロジック設計

### 7.1 基本方針

- SIM種別は判定条件に含めない
- 申し込み方法は判定条件に含める
- 現在の質問にない `returning`, `router`, `undecided`, `any`, `attributes` 系条件は使わない
- 公式ページ上で併用不可と明記されていないキャンペーン同士は、併用可として扱う
- 終了済み・開始前キャンペーンはランキング対象外
- ランキングはキャンペーン単体ではなく、併用キャンペーン合算ポイントTop5

### 7.2 日付判定

現在日付を `today` として判定する。

- `today < startDate` のキャンペーンは除外
- `endDate` が存在し、`today > endDate` のキャンペーンは除外
- `endDate` が `null` の場合は終了日未定として有効
- 終了日当日は有効
- 日付が不正なキャンペーンは安全側として除外

### 7.3 条件一致判定

キャンペーンの `eligibility` とユーザー入力を照合する。

- キャンペーン側の条件配列が空なら常に一致
- 条件配列が空でない場合、ユーザー入力が含まれていれば一致
- `purchase_plan` が空のキャンペーンは購入予定条件なしとして一致
- `rakuten_card` が空のキャンペーンは楽天カード条件なしとして一致
- `application_method` が空のキャンペーンは申し込み方法条件なしとして一致

### 7.4 除外条件判定

キャンペーンの `exclusions` にユーザー条件が該当する場合は除外する。

- `exclusions.conditions` に一致したら除外
- `exclusions.application_status` に一致したら除外
- `exclusions.purchase_plan` に一致したら除外
- `exclusions.rakuten_card` に一致したら除外
- `exclusions.application_method` に一致したら除外

除外条件は適用条件より優先する。

### 7.5 候補キャンペーン抽出

以下をすべて満たすキャンペーンを候補にする。

- 日付が有効
- 適用条件に一致
- 除外条件に該当しない
- `point > 0`
- `officialUrl` が存在する

候補キャンペーンは `point` 降順、`priority` 降順で並べる。

組み合わせ生成前に上位20件までに制限する。  
20件を超える候補は初期公開では組み合わせ対象にしない。

### 7.6 組み合わせ生成

候補キャンペーンから併用可能な組み合わせを生成する。

除外ルール:

- キャンペーンAの `cannotCombineWith` にキャンペーンBの公式キャンペーンコードが含まれる場合、A+Bは不可
- 逆方向も同様
- 同じ `combinationGroup` に属するキャンペーンは原則1つだけ選ぶ
- `combinationGroup = null` のキャンペーンは複数併用可

併用ルール:

- `cannotCombineWith` に含まれていないキャンペーン同士は併用可
- 公式上で併用可否が不明でも、データ上で併用不可登録されていなければ併用可として扱う

### 7.7 ポイント計算

各組み合わせの合計ポイントを計算する。

```ts
totalPoint = campaigns.reduce((sum, campaign) => sum + campaign.point, 0);
```

同じキャンペーンIDを重複して含めない。

### 7.8 重複排除

同じキャンペーンID集合の組み合わせは1件にまとめる。

例:

- `A + B + C`
- `B + A + C`

この2つは同一扱い。

### 7.9 ランキング

生成した組み合わせを以下の順で並べる。

1. `totalPoint` 降順
2. 組み合わせ内の最高 `priority` 降順
3. キャンペーン数が少ない順

Top5のみ結果ページに渡す。

### 7.10 ランキング結果型

```ts
type RankingResult = {
  rank: number;
  totalPoint: number;
  mainBannerImage: string;
  campaigns: Array<{
    campaignCode: string;
    name: string;
    point: number;
    officialUrl: string;
  }>;
  userActions: string[];
  deadlineLabel: string;
};
```

`mainBannerImage` は、組み合わせ内で最もポイントが高いキャンペーンの `bannerImage` を使う。  
同ポイントの場合は `priority` が高いキャンペーンを使う。

`deadlineLabel` は、組み合わせ内で最も早く終了するキャンペーンの期限を表示する。  
すべて終了日未定の場合は「終了日未定」と表示する。

## 8. エッジケース

- 条件に合うキャンペーンが0件の場合: 「対象キャンペーンが見つかりませんでした」を表示
- Top5未満の場合: 存在する件数だけ表示
- バナー画像がない場合: 汎用のキャンペーン画像、またはCSSバナーを表示
- 公式URLがないキャンペーン: ランキング対象外
- ポイントが未設定または0以下: ランキング対象外
- 日付が不正なキャンペーン: ランキング対象外
- データ読み込み失敗: データエラー表示

## 9. デザイン方針

参考画像の方向性:

- 白背景
- 楽天ピンクをメインカラー
- 上部にピンク帯ヘッダー
- その下に広告・PRと最終更新日
- ファーストビューで課題と価値を強く訴求
- 5問フォームは枠線付きの診断ボックス
- 選択肢は大きいカード型ボタン
- 選択中はピンク背景、チェックアイコン表示
- 結果ページは順位リボン + バナー + ポイント + 条件 + 期限 + 公式リンク
- 公式リンクはピンク枠ボタン

### 素材方針

人物イラスト、アイコン、バナー素材がある場合は画像を使う。  
ない場合はCSS/HTMLで代替してよい。

ただし、キャンペーン名・ポイント数・条件など、更新頻度が高いテキストは画像に焼き込まない。HTMLデータとして表示する。

### 画像素材を置く場合

推奨配置:

```text
images/
  hero-woman.png
  hero-man.png
  icon-gift.png
  icon-phone.png
  icon-coin.png
  icon-crown.png
```

キャンペーンバナーはキャンペーン情報と一緒に管理する。

```text
data/
  campaigns/
    items/
      index.json
      campaign-item-1.json
      campaign-item-2.json
    banners/
      campaign-banner-1.png
      campaign-banner-2.png
      campaign-banner-3.png
      campaign-banner-4.png
      campaign-banner-5.png
```

キャンペーンバナーは、背景・装飾だけ画像にし、キャンペーン名やポイントはHTMLで重ねるのが望ましい。

### フォント方針

添付画像に近づける場合は、太めの丸ゴシック系を使う。

候補:

- `M PLUS Rounded 1c`
- `Noto Sans JP`
- `Zen Maru Gothic`
- `Hiragino Sans`

Web公開する場合はライセンスを確認する。Google Fontsを使うなら `M PLUS Rounded 1c` または `Noto Sans JP` が安全。

## 11. テスト観点

最低限、以下を確認する。

- 開始前キャンペーンが除外される
- 終了済みキャンペーンが除外される
- 終了日当日のキャンペーンが含まれる
- 終了日未定キャンペーンが含まれる
- 新規契約・MNPで結果が変わる
- SIMのみ・iPhone・Android・ルーター・未定で結果が変わる
- Web限定・店舗限定・どちらでもよいで結果が変わる
- 22歳以下、家族、楽天カードなど複数属性が反映される
- 除外条件に該当するキャンペーンが表示されない
- `cannotCombineWith` の組み合わせが除外される
- 同じ `combinationGroup` のキャンペーンが同時に入らない
- 併用可のキャンペーンが合算される
- 合計ポイント順にTop5が表示される
- 同点時に最高優先度、キャンペーン数で並び替えられる
- バナーは最高ポイントキャンペーンのものが使われる
- 該当なし表示が崩れない
- データ読み込み失敗時にエラー表示される
- スマホ幅で横スクロールが出ない
- PC幅で参考画像に近い余白・カード配置になっている
- フォーム送信でURLパラメータが正しく付与される
- 結果ページを直接開いてもURLパラメータから診断できる

## 12. 運用方針

キャンペーン情報の更新は手動管理を前提にする。

更新時に最低限確認する項目:

- キャンペーン名
- 最大獲得ポイント
- 開始日
- 終了日
- 終了日未定かどうか
- 対象条件
- 対象外条件
- 併用不可条件
- 公式URL
- 最終確認日

更新頻度の目安:

- 通常時: 週1回
- 大型キャンペーン時: 必要に応じて随時
- 終了日が近いキャンペーン: 終了日前後に確認

今後このプロジェクトで作業するCodexは、以下を守る。

- 作業前にこの文書を読む

- 判定ロジック変更時はテストケースを追加または手動検証ログを残す
